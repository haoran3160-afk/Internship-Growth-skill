# 理解模式

## 目标

围绕一个真实功能、Bug、PR 或代码问题建立足以行动的心智模型。不要承诺一次理解整个大型仓库。

## 1. 划定问题

明确以下内容：

- 用户或调用方想完成什么。
- 本次追踪的起点、成功终点和不包含内容。
- 学习者最想回答的问题。

用户没有指定范围时，选择一个有可见入口和可验证结果的代表性链路。

## 2. 按证据阅读

只读取解释当前链路所需的内容：

1. 仓库说明、manifest、入口与相关配置。
2. 前端路由、组件、状态或调用端。
3. HTTP、RPC、IPC、事件或消息边界。
4. 后端 handler、service、domain rule 或任务处理器。
5. repository、ORM、schema、migration 或外部适配器。
6. 能确认行为的测试、fixture 和运行结果。

只记录实际存在的层。没有数据库或后端时明确写“本链路不存在”，不要套用通用架构。

## 3. 建立链路

先记录证据快照：

- `source_repository`：公开仓库可写 URL 或名称；个人笔记引用私有仓库时只写获准别名或 `private-source`。
- `source_ref`：对已提交快照记录完整 commit SHA。Tag、branch 和 PR 编号只能写入可选的 `source_label`，并解析到 commit SHA；它们本身不算不可变引用。
- 工作区含未提交内容时，将 `source_ref` 写为 `working-tree@<base-commit-sha>`，并明确该引用不可复现。
- `verified_at`：本次核对证据的日期。

按目标位置选择证据表示：

| 目标位置 | 允许的证据表示 |
|---|---|
| 公司批准的位置或公开仓库 | `source_repository`、commit `source_ref`、可选 `source_label` 和相对 `path:line` |
| 个人脱敏位置 | `private-source`、`source_ref: withheld`、`verified_at`、`E1` 等只在本笔记内有意义的句柄；不写内部路径、schema 或接口标识 |

个人句柄只能说明“曾在获准环境核对”，不能让个人笔记获得独立可复核性。需要复核时回到获准位置或原始来源；不要建立公司证据到个人笔记的可逆映射。

为每个关键跳转记录：

| 字段 | 要求 |
|---|---|
| 业务步骤 | 谁在做什么、为什么 |
| 代码节点 | 组件、函数、类型或数据表 |
| 输入与输出 | 数据如何变化 |
| 下一跳 | 控制或数据为何移动 |
| 证据 | 目标位置允许时使用仓库相对 `path:line @ source_ref`；个人脱敏位置使用 `E1` 等不可反查句柄 |
| 置信度 | `confirmed`、`inferred`、`unknown` |

优先解释业务规则、权限、验证、状态变化、事务和失败路径；框架知识只解释它在当前链路中的作用。

## 4. 交付解释

按以下顺序输出：

1. 一句话业务结论。
2. 端到端链路。
3. 关键数据与规则。
4. 失败路径和验证证据。
5. 尚未确认的事实及下一步检查。

用户要求保存时，填写 `assets/feature-trace.md`。把当前链路涉及的术语直接写进该模板，不另建全局词典或系统地图。

## 5. Teach-back

根据当前链路只提出一个检索问题并停止，不要在同一输出中给答案。例如：

- 请不看笔记复述数据从入口到结果的过程。
- 如果新增一个字段，需要改动哪些节点，为什么？
- 出现某个失败现象时，你会先检查哪里？
- 哪个结论仍是推断，如何验证？

等待学习者回答后，只纠正最小误解，再用一个变体确认。代理自己的总结、自答或附带答案不能证明学习者已经理解。

## 完成标准

- 范围是一个具体问题而不是整个仓库。
- 证据记录了适合目标位置的来源表示和 `verified_at`；工作区引用与个人句柄的不可复现性已明确标记。
- 关键跳转都有证据或明确标为未知。
- 输出包含业务、运行时、实现和验证四个视角中实际相关的部分。
- 已提出 Teach-back；只有学习者作答并通过后才标记理解完成。
