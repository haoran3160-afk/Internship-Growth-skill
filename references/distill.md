# 沉淀模式

## 目标

把已经理解的实现转化为可迁移的工程知识，而不是收藏一段看起来高级的公司代码。

## 1. 判断是否值得沉淀

至少满足两项才创建永久笔记：

- 解决跨项目可能重复出现的问题。
- 包含重要不变量、边界或取舍。
- 能避免正确性、安全、并发、性能或可维护性缺陷。
- 展示值得练习的架构或框架机制。
- 学习者能够脱离原代码解释并重新实现。

普通语法、未理解的片段和只适用于单次业务规则的代码，不创建模式笔记；直接说明为什么暂不沉淀。

## 2. 提取模式

按以下结构分析：

1. **问题与上下文：** 什么会失败，受哪些约束。
2. **核心不变量：** 无论实现如何变化，什么必须成立。
3. **机制：** 控制、数据、状态和失败处理如何维护不变量。
4. **取舍：** 替代方案、成本和选择条件。
5. **适用边界：** 何时使用，何时不要使用。
6. **验证：** 正常、失败、边界或并发测试如何证明它。

## 3. 独立重写个人示例

个人 Obsidian 示例必须同时满足：

- 关闭或移开公司来源后，从通用原理重新设计。
- 使用不同领域、数据形状、命名和结构。
- 不包含内部项目名、仓库路径、环境变量、接口名、工单或真实业务数据。
- 小到能看见核心机制，但完整到可以运行或严格推理。
- 包含预期行为和至少一个失败导向的验证。

机械替换类名、变量名或删除注释不算独立重写。若无法安全重写，只在获准的公司位置记录原始学习，不生成个人版本。

## 4. 限定默认输出

无论直接回答、生成 Obsidian 草稿还是保存文件，只要用户没有明确点名额外章节，就按以下固定契约输出：

1. 一个工程模式：名称，加不超过三句话的问题与机制说明。
2. 一个核心不变量。
3. 一个独立重写的最小示例。
4. 一至三个能证明不变量的验证。
5. 一个主要取舍：同时说明主要收益、代价和选择条件。
6. 一个迁移题。

用户要求 Obsidian 草稿或保存文件时，使用 `assets/engineering-pattern.md`。只有用户明确点名额外章节时才增加这些章节，仍只围绕一个模式。不要附上整段来源代码；只保留能说明通用模式的最小独立示例。

最后给出一个迁移题：换一个技术栈或业务场景，学习者将如何保持同一不变量？

## 完成标准

- 候选通过复用价值判断。
- 对话、草稿和保存文件默认都符合“一模式、一不变量、一示例、一至三个验证、一取舍、一迁移题”。
- 个人示例可独立解释，且不能反向识别公司实现。
- 学习者能回答迁移题；未回答时只标记为待验证，不宣称已掌握。
