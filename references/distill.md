# 沉淀模式

## 目标

把已经理解的实现转化为可迁移的工程知识，而不是收藏一段看起来高级的公司代码。

## 1. 判断是否值得沉淀

至少满足两项才创建永久笔记：

- 解决跨项目可能重复出现的问题。
- 包含重要不变量、边界或取舍。
- 能避免正确性、安全、并发、性能或可维护性缺陷。
- 展示值得练习的架构或框架机制。
- 学习者能够脱离原代码解释并重新实现。

普通语法、未理解的片段和只适用于单次业务规则的代码不创建模式笔记；直接说明为什么暂不沉淀。

## 2. 提取模式

按以下结构分析：

1. **问题与上下文：** 什么会失败，受哪些约束。
2. **适用边界：** 何时使用，何时不要使用。
3. **核心不变量：** 无论实现如何变化，什么必须成立。
4. **工作机制：** 控制、数据、状态和失败处理如何维护不变量。
5. **验证：** 正常、失败、边界或并发测试如何证明它。
6. **主要取舍：** 收益、代价、替代方案和选择条件。

## 3. 独立重写个人示例

个人 Obsidian 示例必须同时满足：

- 关闭或移开公司来源后，从通用原理重新设计。
- 使用不同领域、数据形状、命名和结构。
- 不包含内部项目名、仓库路径、环境变量、接口名、工单或真实业务数据。
- 小到能看见核心机制，但完整到可以运行或严格推理。
- 包含预期行为和至少一个失败导向的验证。

机械替换类名、变量名或删除注释不算独立重写。若无法安全重写，只在获准的公司位置记录原始学习，不生成个人版本。

## 4. 使用阅读优先的默认输出

用户没有明确点名额外章节时，只围绕一个模式按以下顺序输出：

1. 模式解决的问题。
2. 适用场景与边界。
3. 一个核心不变量。
4. 维护不变量的工作机制。
5. 一个独立重写的最小示例。
6. 一至三个能证明不变量的验证。
7. 一个主要取舍，包括收益、代价和选择条件。

用户要求 Obsidian 草稿或保存文件时，使用 `assets/engineering-pattern.md`。不要附上整段来源代码；只保留能说明通用模式的最小独立示例。

## 5. 按需检查迁移能力

用户明确要求迁移练习、检查掌握程度，或主动尝试把模式用于新场景时，才提出一个迁移问题。问题应更换技术栈或业务场景，同时要求保持同一不变量。

用户没有请求学习检验时，不在笔记末尾强制添加迁移题，也不使用 `pending` 状态暗示任务未完成。没有学习者回答时，不声称其已经掌握或能够迁移。

## 完成标准

- 候选通过复用价值判断。
- 默认结果包含一个模式的问题、边界、不变量、机制、独立示例、一至三个验证和主要取舍。
- 个人示例可独立解释，且不能反向识别公司实现。
- 用户未明确要求时不附迁移题；要求学习检验时仍能生成有意义的迁移问题。
