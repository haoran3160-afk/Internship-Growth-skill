# 经历模式

## 目标

从真实工作事实生成可信记录或面试材料。表达强度来自具体行动、判断和验证，不来自扩大归属或编造数字。

## 1. 建立事实

优先使用用户确认的职责、行动、反馈和结果。Commit、PR、Issue、测试或评审记录可以证明某项活动存在，但不能单独证明：

- 当前用户是作者或负责人。
- 方案、根因或关键决策属于当前用户。
- 变更已经部署。
- 变更产生了业务指标或避免了损失。

仅有 Git 历史且作者身份未确认时，把它当作待归属证据，不要写“我负责”或“我实现”。

## 2. 通过第一人称门禁

身份门禁先于归属判断。只有同时满足以下条件，才生成第一人称简历 bullet、STAR 或工作记录：

1. 用户明确确认相关提交、任务或行动属于自己，或者提供可核验的“当前用户 ↔ 作者”身份映射。
2. 用户的具体责任和行动至少有一项得到确认。

“整理成我的经历”“帮我写简历”等请求措辞不构成身份确认；仓库本地 Git 配置、提交作者一致和目录位于用户设备上也不构成当前用户映射。

任一条件缺失时，不使用 `owned`、`contributed` 或 `observed` 描述当前用户，也不生成第一人称草稿。本次按固定形状输出“待确认事实包”：

1. **可确认事实：** 记录中发生过的变更和验证，不归属于任何人。
2. **不能确认：** 当前用户身份、责任、决策权、部署和业务影响。
3. **最少补充问题：** Git 作者是否为本人、本人负责模块、方案决策者、实际验证和部署结果。

不要先写一版第一人称故事再加免责声明；没有通过门禁就不生成故事。

## 3. 逐条陈述归属

先把任务拆成最小可核验陈述，再为每条陈述使用一个主要标签。标签回答“这条行动或决策是谁完成的”，不回答“整个项目归谁”：

| 标签 | 含义 | 安全表达 |
|---|---|---|
| `owned` | 有证据表明学习者独立完成这条具体行动或决策 | “我独立完成……” |
| `contributed` | 有证据表明学习者共同完成这条行动，或在指导下完成其中有边界的部分 | “我参与……，具体完成……” |
| `observed` | 这条陈述描述 Leader、同事或团队的行动、设计与决策；学习者只阅读、旁听或学习 | “我了解到团队……” |

同一任务必须拆开来源设计和学习者行动：Leader 定位根因是 `observed`；学习者在该方案下落实修复可能是 `contributed`；学习者自己复现问题、执行验证或独立设计回归测试，可以按该条行动的证据标为 `owned` 或 `contributed`，不能因为所学方案来自他人就统一标为 `observed`。

每条陈述同时记录：

- `evidence_status`：`verified`（已检查工件或运行结果）、`user-confirmed`（用户第一手确认但未独立核验）、`inferred` 或 `unknown`；同一条可组合多个状态。
- `evidence_source`：`user`、`git`、`pr`、`issue`、`test`、`runtime`、`review` 或 `other`。

用户确认可以证明其自述身份、责任和行动，但不能单独把部署、指标或因果状态升级为 `verified`。

## 4. 记录工作

用户要留痕时，填写 `assets/worklog.md`：

- 背景和分配给学习者的责任。
- 实际行动、决策者、归属和证据。
- 验证结果与尚未验证内容。
- 学到的业务或技术知识、反馈和下一步。

把 Leader 或同事的设计直接作为一条 `observed` 记录，不另建 Shadow Learning 系统。

## 5. 生成面试材料

用户要简历或面试内容时，先检查事实记录，再使用 `assets/interview-story.md`：

- Situation：脱敏背景和问题价值。
- Task：学习者的真实责任及不属于其责任的部分。
- Action：学习者实际分析、实现、沟通和验证的内容。
- Result：直接观察到的结果；没有指标时使用定性结果。
- Reflection：取舍、学习和改进方向。

每个重要陈述都应能回到证据或用户确认。缺失指标时不要估算百分比、用户量、延迟、收入或避免损失。

## 完成标准

- 身份门禁通过后，每条最小工作陈述都有归属、逐条 `evidence_status` 和 `evidence_source`；门禁未通过时只交付待确认事实包，不做个人归属。
- 作者、决策者、部署和影响的未知项没有被自动补全。
- 简历和 STAR 只使用已确认事实，保留必要的脱敏边界。
- Leader 或团队成果没有被写成个人所有。
