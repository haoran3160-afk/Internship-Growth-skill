# Internship Growth 理解体验最小升级设计

## 状态

- 方向：已由用户选择方案 1。
- 范围：只改善理解与沉淀体验，不增加新模式。
- 实现：等待用户复审本规格后再制定实施计划。

## 背景与问题

当前 Skill 能围绕具体链路提供证据、隐私边界和不确定性标记，但真实使用暴露了三个问题：

1. 理解模式强调证据链，缺少面向实习生的解释深度，结果可能正确却仍然看不懂。
2. Teach-back 和迁移题是强制完成条件，正常解释容易在结尾突然变成考试。
3. 保存模板以元数据和证据表为中心，不符合“先建立心智模型，再核验证据”的阅读顺序。

问题的本质不是功能数量不足，而是输出契约没有把“可理解性”定义成可观察结果。

## 设计目标

本次升级必须做到：

1. 默认输出足以让没有仓库背景的实习生理解业务、架构、运行链路和关键代码之间的关系。
2. 根据用户意图选择解释深度，不把概览写成教程，也不把深度讲解压缩成摘要。
3. 将业务理解、架构拆解、逐段或逐行代码解释、逻辑图、第一性原理和逆向拆解设计为理解模式的按需能力。
4. 将 Teach-back 和迁移题改为可选学习检验，不再阻塞正常交付。
5. 让对话输出和保存模板先服务阅读，再服务证据归档。
6. 保持现有证据、隐私、真实性和归属门禁不变。

## 非目标

本次不做以下事项：

- 不增加“任务规划”第四模式。
- 不增加通用会议总结能力。
- 不增加 Dashboard、周报、长期状态、自动同步或外部依赖。
- 不增加运行时脚本。
- 不扩大第一人称经历、内部内容导出或公开发布权限。
- 不承诺一次解释整个大型仓库。

## 不可变主线

升级后仍遵循：

> 一次调用 → 一个具体任务 → 一种模式 → 一份有证据的结果 → 明确停止

三种现有模式保持不变：理解、沉淀、经历。本次只调整理解模式的解释方法、沉淀模式的默认结束方式，以及两个对应模板的阅读结构。

## 能力分层

新增能力不得直接等同于新模式。理解请求从以下三个维度组合：

| 维度 | 选项 | 选择依据 |
|---|---|---|
| 解释深度 | 概览、详细、代码下钻 | 用户措辞、输入范围和任务目的 |
| 分析视角 | 业务、架构、运行链路、代码、第一性原理、逆向追踪 | 当前问题真正需要回答什么 |
| 表达形式 | 分层说明、表格、逻辑图、代码注释式解释 | 哪种形式最能降低理解成本 |

仓库、代码片段、PR、Bug、测试、业务文档和会议记录只是输入来源，不因此产生新模式。会议材料只有在用于理解业务、技术决策或当前链路时才属于理解模式；普通会议纪要不在本 Skill 范围内。

## 解释深度

### 概览

仅在用户明确要求“快速了解”“先看全貌”或输入范围很大且尚未选定链路时使用。

输出包含：

1. 业务目标。
2. 主要参与者或组件。
3. 一条主链路。
4. 当前最值得继续下钻的位置。

### 详细

这是实习生理解请求的默认深度。

输出包含：

1. 当前问题与一句话结论。
2. 业务背景：参与者、目标、规则和成功结果。
3. 心智地图：系统边界、主要组件及其职责。
4. 运行链路：请求、数据、状态或事件如何移动。
5. 关键实现：重要函数或代码块做什么、为什么这样做。
6. 数据与状态：核心对象、字段变化、持久化和一致性要求。
7. 失败与验证：异常路径、边界条件、测试或运行证据。
8. 已确认事实、合理推断和仍未知内容。

只输出当前链路实际存在并且有助于理解的章节；不得为了满足结构而编造不存在的层。

### 代码下钻

用户明确要求逐行、逐段或深入解释某个文件、函数、类或代码区间时使用。

执行规则：

1. 先说明该代码在业务链路中的位置和调用上下文。
2. 先按逻辑块划分，再解释块内关键行；只有用户明确要求时才覆盖每一行。
3. 每个逻辑块解释“做什么、为什么、输入输出、状态或副作用、下一跳”。
4. 语法、框架或语言机制只在其影响当前行为时解释。
5. 引用精确 `path:line`，但不让引用替代自然语言解释。
6. 输入范围过大时，先选择最关键区间并说明未覆盖部分。

## 分析视角

### 业务理解

从参与者、目标、规则、状态变化和成功或失败结果出发，再映射到代码。不得先罗列目录或框架名。

### 架构拆解

同时解释静态职责和动态协作：

- 静态：组件、边界、依赖方向和数据归属。
- 动态：一次真实请求或事件如何穿过这些组件。

只有当前问题需要时才解释前端、后端、数据库、消息系统或外部服务；不强行补齐完整技术栈。

### 逻辑图

当存在至少三个重要节点、明显分支、状态变化或跨边界交互时，可以使用 Mermaid 图。图必须：

- 只包含有证据支持的节点和关系。
- 区分已确认与推断关系。
- 配一段文字解释读图顺序和关键结论。

简单线性链路使用短列表或表格，不为了“看起来专业”强制画图。

### 第一性原理

仅在用户询问设计原因、架构取舍或“为什么不能更简单”时使用。输出顺序为：

1. 必须满足的约束。
2. 不可破坏的不变量。
3. 满足不变量的最小机制。
4. 当前实现增加的复杂度及其原因。
5. 可行替代方案和选择条件。

不得用抽象哲学语言代替仓库证据。

### 逆向拆解

当用户从页面结果、接口响应、错误现象、测试失败或数据库状态开始提问时，从可观察结果逆向追踪：

1. 谁产生了这个结果。
2. 它依赖哪些输入和状态。
3. 上一跳由谁调用或写入。
4. 哪条业务规则决定了当前行为。
5. 最早可以验证或改变行为的位置在哪里。

逆向追踪最终仍应与正向运行链路相互核对。

## 输出与证据规则

对话默认采用“先建立地图，再逐层下钻”的阅读顺序。证据放在所支持的结论旁边，不先输出独立的大型证据表。

每个关键解释至少回答以下问题中的相关项：

- 它是什么？
- 它为什么存在？
- 它接收什么、产生什么？
- 它与上一层、下一层如何连接？
- 它改变了什么数据或状态？
- 它失败时会发生什么？
- 这个结论如何确认？

专业术语第一次出现时使用一句话解释，并立刻说明它在当前链路中的作用。不得把概念定义和当前代码解释割裂成两篇内容。

## 学习检验

Teach-back 和迁移题不再作为默认输出或完成条件。

只有满足以下任一条件时才提供学习检验：

- 用户明确要求“考考我”“检查我是否理解”或类似交互。
- 用户主动回答、复述或尝试迁移当前知识。

用户没有请求学习检验时，以完整解释、证据状态和可选下钻方向结束，不向用户布置问题。

沉淀模式保留迁移能力作为质量目标，但不强制在每篇笔记末尾生成迁移题。需要验证迁移时，再单独提出问题。

## 验收场景

### 应产生详细解释

请求：“我是刚入职的后端实习生，看不懂订单创建链路，请从业务到代码详细讲清楚。”

验收：默认使用详细深度；建立业务和架构地图；解释运行链路、关键代码、数据状态及失败路径；证据贴近结论；结尾不强制 Teach-back。

### 应保持概览

请求：“我刚拿到这个仓库，先用五分钟告诉我它解决什么问题和主链路。”

验收：输出业务目标、主要组件、主链路和下钻建议；不展开逐行代码。

### 应进入代码下钻

请求：“逐行解释 `createOrder`，特别说明每个校验为什么存在。”

验收：限定在目标函数；先建立上下文和逻辑分块，再解释关键行、业务原因、输入输出和副作用。

### 应生成逻辑图

请求：“画出前端提交订单到库存扣减和支付创建的调用关系。”

验收：存在三个以上跨边界节点时生成图，并用文字解释关键路径；推断关系明确标记。

### 应使用第一性原理

请求：“为什么订单创建要拆成校验、预占库存和支付三个步骤？能不能一个事务完成？”

验收：从约束、不变量、最小机制、额外复杂度和替代方案回答，不输出泛化哲学。

### 应使用逆向拆解

请求：“页面显示库存不足，这个错误最可能从哪里产生？请从页面往后追。”

验收：从可观察结果逆向追踪到产生者、依赖状态、上游调用和业务规则，并与正向链路核对。

### 不应强制学习检验

请求：“把这个幂等设计整理成 Obsidian 笔记。”

验收：输出完整模式笔记，但不附迁移题；除非用户另外要求检查掌握程度。

### 不应扩大范围

请求：“帮我总结今天所有会议并安排未来一个月工作。”

验收：不将其吸收到理解模式；说明通用会议总结和长期工作管理不属于本次升级。

## 验证方法

实现前先保存当前 Skill 对上述场景的基线输出，确认以下失败确实存在：

- 解释只给链路结论，缺少业务、架构或代码之间的联系。
- 默认结尾强制出现 Teach-back 或迁移题。
- 保存模板以宽表和元数据为主，阅读顺序不自然。

实现后使用相同输入复测，并检查：

1. 可理解性：新手能否回答“为什么、怎么流动、在哪里修改、如何验证”。
2. 证据完整性：关键结论仍有来源或不确定性标记。
3. 深度匹配：概览不冗长，详细解释不空泛，代码下钻不失控。
4. 模式纯度：没有生成任务规划、会议系统或长期状态。
5. 交互自然度：用户未要求时不出现考试式问题。
6. 隐私安全：内部内容边界与现有规则一致。

将上述输入、预期行为和基线失败记录在 `evals/understanding-experience.md`，让后续修改可以复用同一组回归场景。完成实现后运行官方 `quick_validate.py`，并分别执行正例、负例和边界场景复测。

## 风险与控制

| 风险 | 控制方式 |
|---|---|
| 默认输出变得过长 | 使用三档深度；只输出当前问题相关章节 |
| 逻辑图制造不存在的关系 | 图中关系必须有证据，推断单独标记 |
| 逐行解释退化成语法翻译 | 先讲业务位置和逻辑块，只解释影响行为的语法 |
| 第一性原理变成空泛套话 | 强制从当前约束和不变量出发，并回到代码证据 |
| 取消强制问题后缺少学习验证 | 保留按需学习检验，不把它作为默认交付仪式 |
| 模板简化后证据不足 | 保留 frontmatter 和贴近结论的证据字段 |

## 完成标准

本次升级完成时必须同时满足：

- 三种模式和“一次一个任务”主线不变。
- 详细解释成为实习生理解请求的默认行为。
- 六种理解视角可以按需组合，但不会变成六个新模式。
- Teach-back 和迁移题不再强制出现。
- 两个模板按阅读顺序组织，同时保留证据与隐私信息。
- 所有验收场景通过，Skill 校验成功。
- README 中的能力、示例和边界与实际行为一致。
